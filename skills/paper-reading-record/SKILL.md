# 论文阅读记录

把一篇论文 + 它的官方代码仓库，写成一份「先给结论、证据可复核」的阅读记录，正文关键机制处嵌入本地化的论文原图，末尾调用 `hand-drawn-poster` 技能输出一页手绘总体一览。记录的目的不是复述论文，而是回答：**这篇论文的核心机制是什么、论文声称与已验证事实的边界在哪、我们的工作值不值得借鉴、借鉴的前提是什么。**

## 触发场景

- 精读一篇论文后要沉淀成可分享文档
- 技术选型调研，需要判断某论文方案是否适用于我们的系统
- 论文有开源仓库，需要核对「论文描述」与「代码实际行为」是否一致
- 评估复现可行性（数据、基准、超参是否真的可用）

## 开工前先确认材料

缺任何一项，先问用户，不要靠猜测填补：

| 项 | 用途 | 缺失时 |
|---|---|---|
| 论文原文链接（arXiv abs / html / pdf） | 所有图表公式的引用锚点；HTML 版决定原图能否直接提取 | 必须获取，否则无法写 |
| 官方代码仓库地址 | 「当前代码」栏的依据 | 无公开代码时按降级规则处理 |
| 基准 commit 与包版本 | 锁定源码分析对象 | 读代码前补齐，仓库更新后记录会失效 |
| 论文许可协议（CC BY 4.0 / arXiv non-exclusive 等） | 图表引用声明 | 从论文页脚或 project 页确认 |
| 要对照的自研系统 | 结论摘要的判断对象 | 由用户指定，写明系统名 |
| 各项网络核查的执行日期 | 复现条件表的时效标注 | 用实际核查当天日期 |

## 固定骨架

四段式，顺序不能调整——结论前置，细节和原始数据后置。完整带占位符的模板见 [template.md](template.md)。

```
> - 论文地址：<链接>
> - 项目仓库：<链接>

# 结论摘要          <- 给不读全文的人，30 秒内能拿到判断
  ## 核心判断        <- 对照自研系统，3 条左右；结尾给「取舍」
  ## 核心实现说明    <- 一张 mermaid 流程图 + 论文总体架构原图（或显式交叉引用）+ 编号小节，逐条「论文设计 / 当前代码」对照

# 论文解读          <- 只讲论文本身，不掺代码
  ## 1. 研究背景与目标   目标 / 应用约束 / 现有问题 / 作者的切入点 / 一句分析
  ## 2. 技术方案         分机制拆解，末尾一节「论文设计与代码实现的对应关系」
  ## 3. 实验评估         设置、主要结果、效率与开销、消融、迁移、定性案例
  ## 4. 研究局限与借鉴价值 指标口径 / 复现条件 / 借鉴价值与验证条件

# 项目解读          <- 依据基准 commit 的源码分析
  ## 1. 项目定位与功能范围  模块职责表
  ## 2. 总体架构与模块职责  mermaid 架构图
  ## 3. 记忆/核心处理流程   主流程、召回、调度
  ## 4. 数据存储与持久化    落盘结构目录树
  ## 5. 应用集成            Demo/服务层行为与已知缺口
  ## 6. 模型配置与部署依赖  模式开关表
  ## 7. 关键代码与评测入口  可直接跑的入口
  ## 8. 端到端时序          并发与状态关系

# 附录
  ## A. 公式与符号说明
  ## B. 完整实验数据        照抄原论文表格，标注表号
  ## C. 参考资料            带版本号的永久链接

# 总体一览（手绘）        <- 调用 hand-drawn-poster 技能生成一页 PNG，正文只嵌引用
```

正文「论文解读」各机制小节就地嵌入提取到本地的论文原图（见「论文原图提取与嵌入」），图随文走，不集中堆在附录。

各章按需裁剪：论文没有配套仓库时省略「项目解读」，全文无公式时省略「附录 A」，不要为凑结构填空。「总体一览」在 Markdown 正文全部交付后才做，是收尾步骤。

项目解读章首除基准 commit 声明外，当论文描述版本与仓库实际版本不同（几乎是常态）时，**必须**附「版本漂移对照表」：`主题 / 论文快照（<论文版本>）/ 当前代码（<commit 短 hash>/<包版本>）/ 代码位置` 四列，逐行列出已核实的差异；每处差异只在此表展开一次（与「信息单一来源」联动），正文其余位置只引用。版本一致时也要写一句「论文版本与代码版本一致，无漂移项」，而不是省略声明。

「项目解读 §3 核心处理流程」与「核心实现说明」的机制清单一一对应：「核心实现说明」编号出现的每个机制，在 §3 必须有对应流程小节（调用链 + 代码引用）；只谈存储结构的内容可放 §4，但「数据如何被读写/召回」属于流程，必须在 §3。

## 核心写法：论文设计与当前代码分栏对照

这是整份记录最有价值的部分。凡是一个机制在论文和代码里都存在的，两条并列写，且**代码行为优先于论文措辞**。

```
**论文设计：**<论文里的机制描述，中性转述>

**当前代码：**<读到的实际行为，含默认值、配置开关、未接入的路径>
```

对照时专门找这几类落差，它们决定能不能落地：

- 论文说「更新/删除旧记录」，代码默认是不是转成追加新记录、要不要开关才生效
- 论文说「自动完成」，代码是否要求显式调用（`flush()`、session 边界、批处理钩子）
- 论文说「端到端某指标」，代码里是否只覆盖了其中一个阶段
- 论文提到的旧链路，在当前代码里是否已无调用方（写了结构但不会被触发）

发现落差就明写出来，并给出后果，例如：不能把「具备冲突判断」直接理解为旧事实已被完整替换。

## 信息单一来源（DRY）

同一个代码级发现（具体默认值、代码路径、论文未披露的行为、版本差异）全文只**展开定义一次**，避免同一事实在摘要、流程节、模式表里各写一遍、措辞漂移后读者无法判断以哪处为准。

- **唯一定义点**：机制事实定义在「项目解读」对应小节，必须带代码引用（pin 到 commit 的文件 + 函数/配置段锚点）。论文版本与代码版本的差异集中记录在项目解读章首的一处对照表中，不散落各节。
- **其余位置只引用**：结论摘要、论文解读、模式表、借鉴价值等小节需要复用时，只写结论句 +「（见项目解读 §x.y）」，不重写默认值与技术细节。
- **自检标准**：若某个事实需要修正，全文应只有一处需要动笔。出现三处以上描述同一行为时，把信息最完整的一处留作定义点，其余降级为交叉引用。

## 证据规则（硬性）

**每一个数字都要能被读者复核。** 具体做法：

1. 引用论文数值时带上出处层级：正文 / 摘要页 / README / 示意图。三者不一致时逐个列出并算出差值来源，例如 `74.16−72.27=1.89`。
2. 区分「报告值」与「系统论断」。`134 ms` 是某子模块的测量报告值，「零延迟」是依赖时间重叠的论断——不能把后者当前者的同义词。
3. 示意图里的文案数值不当作独立测量；与实验正文冲突时以实验正文为报告工作点，并在图注里写明差异。
4. 宣传口径（README 里的总分）无法从论文表格简单平均重建时，直接说无法重建，并指出需要什么额外信息（权重、子集、版本）。
5. 相关不等于因果：t-SNE 投影、单条成功案例只能说明结构或作者期望的产品行为，不能证明检索因果、长期稳定性或普遍成功率。
6. 消融和小幅增益要检查是否缺少重复种子、置信区间、硬件配置、端到端延迟分布；缺就归入复现条件表。
7. 组件成本要算全生命周期：只统计读取侧的 token 与延迟，不能推出总体成本最低（写入、模型归因、维护、无效预取的成本可能未计入）。
8. 引用代码中的可枚举配置默认值（敏感词表、风险等级枚举、provider 目录、模式开关集合）时，要么完整列出全部条目并与代码逐项对齐（如「22 词 = 以下 14 中文 + 8 英文：…」），要么给出可永久定位的引用（pin 到 commit 的 blob 链接 + 函数/配置段名）。只给数量加省略号视为不可复核。

**边界声明用「不能认为 / 不能据此宣称 / 尚不能」明确写出**，不要用「可能有一定局限性」这种模糊措辞。

## 复现条件核查表

「4.2 公开材料与复现条件」用固定三列表，日期写进表头：

| 材料 | <核查日期> 核查结果 | 影响 |
|---|---|---|
| 核心项目 | 本地有 xxx 代码 | 可以分析和尝试运行实现 |
| 训练数据集 | 公开仓库仅列出 README.md | 有公开页面不等于完整数据已可下载 |
| 评测基准 | 论文留待后续报告；作者账号下未检索到 | 本次未确认可获取，不等同于断言所有渠道都没有 |

核查结论必须限定在本次核查动作的范围，不要把「我没找到」写成「不存在」。链接尽量 pin 到具体 commit 或 blob，避免仓库演进后失效。

## 一个例子贯穿全文

选一个具体的用户场景例子（包含 2-3 条可被分别归类的事实），在结论摘要、各机制小节、项目章节里反复复用同一例子说明机制。开头声明：**例子用于说明机制，不代表已经验证的模型输出。**

好例子的特征：事实能天然分到不同类别、涉及第三方人物、带一条情绪——这样才能演示分类、人物关联、情绪归因三条线。

避免用「用户说 A 系统记住 A」这种同义反复的例子。

## 零评测论文的 §3 写法

系统报告型论文（产品论文、开源系统论文）常常没有 benchmark、消融或任何量化评测。此时 §3 不得用功能描述灌水凑节，固定产出三块：

1. **评测缺口清单**：明确列出「论文未给」的指标（成功率、接管率、延迟分布、人工评估等），引论文原话与 roadmap 位置作为证据，而不是猜测作者漏写。
2. **唯一可用的非效果证据**：体积、内存、成本估算等仍值得记录，但逐项标注「估算 / 官方宣传 / 实测」口径，并写明统计范围。
3. **至少一个步骤级机制走查**：用贯穿例子按时间顺序展开 5-8 步（每步模型看到什么、输出什么意图句、哪条策略命中、审批如何触发），放在 §3.5，开头声明「用于说明机制，不代表已验证输出」。它占据定性案例的位置，但性质是机制演示，不是效果证明。

## 图、表、公式规范

- **图**：优先嵌入提取到本地的论文原图（见「论文原图提取与嵌入」），本地相对路径 + `**图 N　标题**（[原论文](链接)）` + 图注。图注里写清这张图能证明什么、不能证明什么，以及与正文的数值差异。仅当原图无法可靠提取时才退回外链，并注明外链可能失效。
- **表**：模块职责、阶段对照、模式配置、部署/运行形态对比、版本漂移一律用表格，不用长段落。论文设计 vs 代码实现的对照表用「阶段 / 论文设计 / 当前代码」三列。
- **正文表与附录表的分工**：附录 B 是原论文表格的逐字照抄（保留全部行列、数值与原注，标表号）；正文表格只做分析性摘录（挑影响判断的行列 + 一句分析），两者不得同构重复，表题互相引用（如「原表见附录 B.1」）。
- **公式**：放附录 A，四件套——原式（保留原文记号）+ **含义** + **符号**逐项解释 + `[对应原式](带锚点的链接)`。论文自身记号含糊的地方（如未解释的下标）明说「保留原样」，不要自行猜测重述。
- **架构图/流程图**用 mermaid，图后补一句限定，例如「图示为主要处理关系，左右分支不表示严格并行执行」。
- 转述与原文分开：图表公式标「引自原论文」并注明许可，中文说明标「为本报告分析」。

## 结论摘要怎么写

摘要部分不写「本文档介绍了 xxx」这类导语，直接给判断：

1. **callout 一句话**：论文侧重的核心 + 我们已有/缺什么 + 主要借鉴点（加粗）。
2. **核心判断 3 条左右**：每条以「**加粗结论。**」开头，随后对照自研系统说明现状，并补一个「但 xxx 取决于 xxx」的条件句。
3. **拆开容易被混为一谈的两件事**：例如模型微调与记忆维护、算法设计与工程接入。说明借鉴某一项不以改动另一项为前提。
4. **取舍**收尾：保留什么、借鉴什么、哪些不足以成为单独启动改造的依据。

自研系统的现状描述必须来自实际代码或已有文档，不能为了衬托论文而虚写。

## 论文原图提取与嵌入

只靠文字转述架构图和消融曲线，读者无法核对「论文到底画了什么」。重要原图必须**提取到本地并嵌入记录**，与正文分析放在一起。

**提取路径（按优先级）：**

1. **arXiv HTML 版**（`arxiv.org/html/<id>v<N>`）：图片以相对路径挂在同名目录下，如 `src="2503.20314v2/vae.png"`，完整 URL 为 `https://arxiv.org/html/2503.20314v2/<相对路径>`。下载 HTML 后用 `img src` + `figcaption` 配对，一次拿到「文件 → Figure 编号 + 题注」索引。
2. HTML 版不存在（老论文）时，用 PDF 工具按页提取（如 `pdfimages -png`），产物需人工与图号配对。
3. 作者项目主页的 demo 图仅作补充，标注来源，不与论文图混编号。

**选图标准——只嵌「改变理解或结论」的图，通常 3-6 张：**

| 类型 | 嵌入位置 | 例 |
|---|---|---|
| 总体架构图 | 结论摘要「核心实现说明」或 §2 开头 | framework / architecture 图 |
| 核心机制图 | 对应机制小节，紧邻「论文设计」段 | VAE 结构、条件构造、并行方案 |
| 关键结果/消融曲线 | §3 主要结果或消融小节 | 与其他 SOTA 的对比图、loss 曲线 |
| 定性案例图 | §3.5，且图注声明「作者挑选的展示样本」 | showcase 拼图 |

纯展示性、与结论无关的图不嵌；记录体积有限，宁缺毋滥。

**图片处置闭环（硬性）：**阶段 2 会下载 scan.json 中的全部图片，但只嵌入 3-6 张——「下载了不用」必须有明确去向，不允许静默遗留。正文定稿后逐一盘点 `<论文简称>-figures/` 下的真实位图，每张三选一：

1. **嵌入**正文合适位置；
2. **有意排除**：在 markdown 中写一行处置注释，逐图给理由，格式 `<!-- figures-disposition: S2_F2=时间线图，与§1文字转述重复; S6_F6=roadmap 已在§4.1 列表覆盖 -->`（分号分隔，图名可带可不带扩展名）；全部图片均已嵌入时整行删除；
3. **bad.json 有失败记录**：按「分阶段自检清单」从 PDF 补取。

总体架构图的位置是硬性的：必须出现在「结论摘要 → 核心实现说明」（紧随自绘 mermaid）**或** §1/§2 开头；放在后者时，核心实现说明节要有一句显式交叉引用（如「论文原始架构见图 1，§2.1」），不能两处都只有文字。

**单篇交付终检：**不只是批量模式，单篇记录在正文定稿、渲染总体一览图之前也要跑一次终检脚本（无 `--plan` 时自动扫描目录下 `p*-论文阅读记录.md`）：

```bash
python3 <skill>/scripts/batch_check.py --root <记录所在目录>
```

其中检查 I（已下载未嵌入）、J（核心实现说明节无原图）为 WARN，不阻断退出码，但必须逐条人工确认——补嵌入或补 disposition 注释后重跑；其余 FAIL 必须清零才能交付。

**落盘规范：**

- 目录：记录同目录建 `<论文简称>-figures/`，文件名保留论文原名（如 `vae.png`），图号写进图注而不是改文件名；论文 HTML 里子目录的图（`figures/t2v/ablation_adaLN.png`）落盘时压平为 `ablation_adaLN.png`，避免重名再保留一级前缀。
- 每张图**必须用 Read 工具读图验收**：确认内容与 figcaption 声称的编号一致（arXiv HTML 偶有图-题错位）、无半页空白、无截断、位图分辨率足以看清轴标签和图例。验收不过关（如导出损坏、只有低清版）就换提取路径重取，仍不行则不嵌图，改为文字转述并在图注位置写明「原图未能可靠提取」。
- 嵌入写法沿用「图、表、公式规范」：本地相对路径 + `**图 N　标题**（[原论文](带 #S4.F5 等锚点的链接)）` + 图注（能证明什么 / 不能证明什么 / 与正文数值口径差异）。

**许可检查前置**：论文若是 arXiv non-exclusive distribution（非 CC BY），记录头部已声明许可类型，嵌入原图属于「引用+评论」用途，图注必须保留「引自原论文」字样和出处链接，不得裁掉作者水印或重绘冒充原创。

## 总体一览图（调用 hand-drawn-poster）

Markdown 正文全部交付后，作为收尾步骤产出一页手绘风 PNG，让不读正文的人一眼拿到「这篇论文在做什么、我们能拿什么」。这一步**必须调用 `hand-drawn-poster` 技能**，按其流程渲染，不要自己从零写 CSS，也不要用 AI 生图模型（中文必糊、无法精确改字）。

**内容取自记录本身，一一对应，不得新造数字或结论。海报区块与 hand-drawn-poster `template.html` 自带组件的对应关系：**

| 海报区块 | 取自记录哪一节 | template.html 组件 | 放什么 |
|---|---|---|---|
| 顶部标题 + 一句话 | 结论摘要 callout | `header h1` + `.sub` | 论文名 + 那句核心判断 |
| 数字气泡（2-4 个） | 主要结果 / 效率 | `.stats > .stat` | 可复核的代表数值，如参数量、压缩比、显存、加权分 |
| 机制卡片（3-5 张） | 核心实现说明各小节 | `.card > .tag` | 每卡「论文设计 / 当前代码」一句，落差用 `.red` 标；若贯穿例子能一句话讲清（情景 + 经过几道门），作为脚注条或独立小卡出现 |
| 论文 vs 开源 对照 | 对应关系表 | `table.rot` | 已开源项 ✓、未开源项标注，一眼看出交付边界 |
| 借鉴取舍 | 结论摘要「取舍」 | 红框卡 + `footer ol` | 保留什么、借鉴什么、哪些不足以立项 |

**执行流程（沿用 hand-drawn-poster 的四步）：**

1. 复制 hand-drawn-poster 的 `template.html` 配方，替换文案写成单页 HTML（宽 1240px），落到记录同目录的 `<主题>/overview.html`。
2. `bash <hand-drawn-poster>/scripts/render.sh overview.html overview.png auto`（macOS 优先 `auto` 自测高度）。
3. **用 Read 工具读 PNG 自查**：裁切、大片空白、字符渲染成方框（□，换稳妥符号）、字体是否降级到手写体。
4. 成品 `cp` 到记录同目录，命名 `<论文简称>-总体一览.png`，在 Markdown「总体一览（手绘）」节嵌入引用，并写明**该图是记录结论的视觉摘要，数字以正文与出处为准**。

图内每个数字必须能在正文找到同值可复核的表述；海报是摘要不是新证据，不引入正文没有的数据或更强措辞。

**图注只写内容事实，不写实现工具（硬性）**：图注固定为「本图是上述记录的视觉摘要：<日期> 生成，图内每个数字均取自正文对应小节，口径以正文为准」形态。**禁止出现渲染工具与流程字样**（如「本图由 xx 技能渲染（HTML -> 无头 Chrome 截图）」）、**禁止暴露本地绝对路径**（记录目录、汇总底稿路径）——实现细节属于本 SKILL.md，不属于交付文档。同理，汇总文档不写「本地文件」一节。

## 输入源与输出去向

**输入源（阶段 1 的四种形态，单篇与批量通用）：**

| 输入源 | 识别方式 | 全文获取 | 图片获取 |
|---|---|---|---|
| arXiv 论文（默认） | `--ids 2610.09934` 或链接里的 id | 抓 HTML 剥离成 TXT | HTML 里 img/graphic/object 引用，`download_figures.py` 下载 |
| HuggingFace 论文页 | `--ids hf:2610.08699`（或完整 `https://huggingface.co/papers/...` 链接；清单里 `source: hf:xxxx`） | HF API（`/api/papers/<id>`）取元信息并入 meta.json（标题/upvotes/github 仓库/星数/项目页/摘要/作者/组织），全文仍从 arXiv 抓——HF 页面本身不含全文 | 同 arXiv 路径 |
| 本地 PDF | `--ids p01=/path/x.pdf --local` 或清单 `pdf:/path/x.pdf` | `pypdf` 逐页抽文本（需 `pip3 install pypdf`） | 无 HTML，直接走 `pypdf` `page.images` 提取（见「降级规则」） |
| 本地 markdown | `--ids p01=/path/x.md --local` 或清单 `md:/path/x.md` | 剥 md 标记成 TXT | 沿用 md 里的本地图片路径（相对该 md 所在目录） |

HF 域名直连失败时脚本自动探测系统代理（macOS `scutil --proxy`、Linux 环境变量与常见本地端口）重试；HF 元信息拿不到只降级提示、不阻塞 arXiv 流程。HF 的 upvotes/星数是社区热度，写进记录时标注为关注度证据而非效果证据。

批量清单（`--from-md`）格式：

```markdown
# 批次清单
## p01 Itgan: NADI 2026 参赛系统
- source: https://arxiv.org/abs/2610.09934
- note: 评注文字（进 meta.intro，汇总表用）

## p02 HF 热门论文
- source: hf:2610.08699

## p03 内部 PDF 材料
- source: pdf:/Users/you/papers/x.pdf

## p04 已整理笔记
- source: md:/Users/you/notes/y.md
```

来源是飞书 wiki 时：先用 `lark-cli` 读 wiki 节点（含子节点）拼出清单文件，再走 `--from-md`。**读取操作**（wiki 列表、`--fetch` 回拉）不修改云端任何数据。

**输出去向（可组合，缺省即本地 markdown）：**

| 去向 | 用到的阶段/脚本 | 说明 |
|---|---|---|
| 仅本地 markdown | 0-4 | 全部产物落 `<records>/`，不碰飞书；最省权限 |
| 本地 + 飞书云文档 | 0-5 | `to_feishu.py` + `create_feishu_docs.py`（建文档需要 lark-cli 登录态） |
| 本地 + 飞书 + 汇总 | 0-6 | 再加 `build_summary.py` + 汇总文档创建 |
| 本地 PDF 版记录 | 4 之后可选 | 想要 PDF 时由用户环境内工具导出（本 skill 不内置 PDF 排版，避免引入不稳定依赖） |

用户没说输出去向时**先问再写**：批量场景建云文档是写操作，宁可多问一句。

## 批量模式（10 篇以上）

一篇时按上文单篇流程走。批量时按**固定管线分阶段推进，阶段间用状态文件衔接，每阶段跑自检脚本**，任何阶段失败可从该阶段重跑而不必重来。以下流程与 `scripts/` 下六个脚本都经过 25 篇实战验证或用真实产物冒烟通过：

- `fetch_arxiv.py` — 阶段 1 抓取 + 图扫描（断点续跑）
- `download_figures.py` — 阶段 2 下载原图 + 魔数校验 + SVG 转 PNG
- `to_feishu.py` — 阶段 5a 飞书 markdown 转换
- `create_feishu_docs.py` — 阶段 5b 批量建云文档（幂等续跑）
- `build_summary.py` — 阶段 6 汇总 md 生成
- `batch_check.py` — 阶段 7 终检（记录 + 图 + 总览 + 飞书链接）

### 管线阶段与状态文件

```
阶段 0  提取论文清单        -> meta.json    [{n, arxiv, title, cat, authors, rating, intro}]
阶段 1  抓取 HTML/TXT      -> <id>.html/.txt + fetch_report.json + scan.json      （fetch_arxiv.py）
阶段 2  下载论文原图        -> <pNN>-figures/<FID>.png + bad.json                  （download_figures.py）
阶段 3  分批撰写记录        -> <pNN>-<短名>-论文阅读记录.md（并行子代理 8-9 篇/批）
阶段 4  渲染手绘总览        -> <pNN>-overview/overview.html + <pNN>-总体一览.png
阶段 5  转换并建飞书云文档  -> feishu-md/*.md + feishu_plan.json + docs.json       （to_feishu.py + create_feishu_docs.py）
阶段 6  建汇总文档          -> 汇总 md -> 汇总云文档 URL                           （build_summary.py + lark-cli）
阶段 7  终检               -> batch_check.py --docs --agg-url 全绿
```

**断点续跑规则**：每个阶段产物落盘即状态——重复执行同一命令时，已存在且合格的产物自动跳过（fetch 的 HTML/TXT、download 的 PNG、飞书文档不重复创建）。中断后直接重跑当前阶段命令即可。

**目录约定**：记录根目录 `YYYY-MM-DD-records/`（与来源 wiki 日期对齐），每篇 `pNN-figures/`、`pNN-overview/`，编号 `pNN` 两位零填充贯穿所有文件名。

### 各阶段命令

```bash
# 阶段 1: 抓取 + 图扫描（5xx 重试 3 次；纯表格论文 figs=0 是正常结果）
python3 <skill>/scripts/fetch_arxiv.py --ids @ids.txt --ids-file --outdir /tmp/<批次>
# 检查 fetch_report.json: html_ok/txt_ok 全 true 才进阶段 2

# 阶段 1 变体（多源输入，见「输入源与输出去向」）:
python3 <skill>/scripts/fetch_arxiv.py --from-md --ids plan.md --outdir /tmp/<批次>
#   plan.md 每篇一段: "## pNN 标题" + "- source: <arXiv链接|pdf:路径|md:路径>" + 可选 note
python3 <skill>/scripts/fetch_arxiv.py --ids p01=/path/p.pdf,p02=/path/n.md --local \
    --outdir /tmp/<批次>   # 本地 PDF(pypdf 抽全文) / markdown 直接作输入

# 阶段 2: 下载图（SVG 自动 Chrome 截图转 PNG；魔数校验防 HTML 占位混入）
python3 <skill>/scripts/download_figures.py --scan /tmp/<批次>/scan.json \
    --outdir <records> --key p01=p01-Itgan --key p02=p02-LIDAccent
# 检查各 pNN-figures/bad.json: "404/placeholder" 的图改从 PDF 提取（见下方降级规则）
# 本地 PDF 输入的篇目没有 scan 条目，图片直接走 pypdf page.images 提取路径

# 阶段 3-4: 按单篇流程撰写与渲染，批量并行用子代理（见下「子代理批量」）

# 阶段 5a: 转 markdown（图片路径 @./ 前缀 + 尖括号 token 转义）
python3 <skill>/scripts/to_feishu.py --root <records> --plan final_map.json \
    --meta meta.json
# 产物: <records>/feishu-md/*.md + feishu_plan.json（pNN -> {file, title}）

# 阶段 5b: 批量创建飞书云文档（幂等：docs.json 已有的 pNN 自动跳过，失败篇目重跑自动重试）
python3 <skill>/scripts/create_feishu_docs.py --plan <records>/feishu_plan.json \
    --docs <批次目录>/feishu_docs.json --cwd <records>

# 阶段 6: 生成汇总 md（按 meta.cat 分组，行内含「打开阅读记录」链接）后创建汇总云文档
python3 <skill>/scripts/build_summary.py --docs <批次目录>/feishu_docs.json \
    --meta meta.json --out <records>/feishu-md/汇总-<批次名>.md \
    --title "<批次名> 论文阅读记录汇总（N 篇）" \
    --source-url <飞书 wiki 链接> --source-name <来源名> --date YYYY-MM-DD
lark-cli docs +create --doc-format markdown --title "<汇总标题>" \
    --content "@./feishu-md/汇总-<批次名>.md"

# 阶段 7: 终检
python3 <skill>/scripts/batch_check.py --root <records> --plan plan.json \
    --docs docs.json --agg-url <汇总文档URL>
```

### 分阶段自检清单

| 阶段 | 异常表现 | 排查与处置 |
|---|---|---|
| 1 抓取 | `html_ok=false` | 404 = HTML 版不存在（老论文），走 PDF 降级路径；5xx/超时先重跑一次（重试内置 3 次） |
| 1 抓取 | `txt_ok=false`（过短） | HTML 抓到了但内容异常（反爬页/验证码页），打开 `<id>.html` 人工看一眼再重跑 |
| 1 扫描 | `figs_found=0` 且论文明显有图 | 打开 HTML 搜 `ltx_figure`；图可能用 `object data=` 挂（扫描器已覆盖 img/graphic/object 三种，新形态需补正则） |
| 2 下载 | bad.json 记 `404/placeholder` | HTML 引用存在但服务端缺文件（arXiv 渲染缺陷）；从官方 PDF 提取该图：`pypdf` 的 `page.images` 取页内嵌图，在记录图注标注「arXiv HTML 404，从 PDF 提取」 |
| 2 下载 | PNG 存在但体积 <10KB | 大概率是 HTML 错误页占位；脚本已按魔数删除，若漏网人工核对再删 |
| 2 下载 | SVG 转 PNG 失败 | 确认 Chrome 路径（脚本自动找 `/Applications/Google Chrome.app`）；`real_svg` 要求开头含 `<svg` 或 `xmlns` |
| 3 撰写 | 子代理只做提取不写文件 | 恢复（resume）子代理并明确指令「现在把文件写到磁盘」；写完核对行数 >= 200 |
| 3 撰写 | 同篇出现两个版本文件 | 立即删除较弱的（图少/行少）版本，保持 25 个文件与 plan 一一对应 |
| 4 总览 | PNG 裁切/空白/方框字 | 按 hand-drawn-poster 的自查迭代高度；emoji 只用稳妥集 ✦ ⚠️ 📌 ⚖️ ● |
| 5 飞书 | `ok=true` 但正文过短 | 创建成功不等于内容完整；`--fetch pNN` 回拉验证正文 >= 3000 字符 |
| 5 飞书 | 批量循环全部报 `unknown command` | `create_feishu_docs.py` 已内置规避（`shell=True` + `shlex.quote`）；自己写循环时不要把 `docs +create` 当单个参数传 `subprocess` 列表 |
| 6 汇总 | 链接数 != 记录数 | 用 `batch_check.py --agg-url` 核验「打开阅读记录」链接与 docs.json 一一对应，缺哪条补哪条 |
| 7 终检 | 任何 FAIL 行 | 每条问题都带括号内的修复提示，修完重跑直到 `RESULT: ALL PASS` |

### 图片下载的三条硬规则（实战踩坑沉淀）

1. **相对路径两种形态都要试**：gfx 引用带 `<id>vN/` 前缀时 URL 是 `https://arxiv.org/html/<gfx>` 原样；不带前缀时是 `https://arxiv.org/html/<id>/<gfx>`。拿 id 给带前缀的引用再拼一层会 404。
2. **体积合格不等于图片合格**：arXiv 404 页是 7882 字节 HTML，只有魔数校验（PNG `\x89PNG` / JPG `\xff\xd8\xff` / SVG 开头 `<svg`）能挡住占位文件。下载后不验魔数就把 404 页当 PNG 嵌入，是本次实战最隐蔽的坑。
3. **同一 figure 锚点挂多张图时文件名加 `_sfN` 后缀**：DNS 语谱图组一个锚点 9 张图，不加后缀会互相覆盖，最后只剩第一张。

### 子代理批量撰写

- 3 个子代理并行，每个 8-9 篇；每篇必给：arXiv id、TXT 全文路径、scan.json/dl_map 的图片映射、模板与成品范例路径、明确文件名。
- **子代理完成消息必须逐篇列：文件名、行数、嵌入图数、核心数字 2 个、复现边界**——只报告「已完成」不落盘的批次要 resume 并重发「写文件」指令。
- 编号映射以 meta.json 为准写进提示词（p16 = 2610.09861 PawCT、p17 = 2610.09318 CASM 这类相邻编号易对调）。
- p01-p25 与 arXiv id 的映射存 `final_map.json`，终检、飞书创建、汇总都从它取文件名，避免目录里文件名漂移。

### 批量飞书创建

阶段 5a/5b/6 的转换、创建、汇总已脚本化（`scripts/to_feishu.py`、`create_feishu_docs.py`、`build_summary.py`），要点如下：

- **转换规则固化在 `to_feishu.py`**：本地图片写 `![alt](@相对路径)` 自动上传；正文里字面 `<token>`（如 `<p>` `<w>`）在反引号外转义成 `\<token\>`，否则被解析成 XML 标签吞掉；代码块与行内反引号内容原样保留。无需手写转换。
- **命令形态坑固化在 `create_feishu_docs.py`**：lark-cli 子命令是 `docs +create` 两个 token，subprocess 列表参数会报 `unknown command`；脚本内用 `shell=True` + `shlex.quote` 拼命令，`--content @./file` 只接受 cwd 相对路径。每篇成功立即落盘 docs.json，中断重跑不丢已建链接。
- 汇总 md 里的「打开阅读记录」字面文案是 `batch_check.py --agg-url` 的核验锚点，`build_summary.py` 固定生成，改文案要同步改两边。
- 创建后抽查：`batch_check.py --fetch pNN,pMM` 回拉 2-3 篇，验证正文 >= 3000 字符、结构完整（四段式标题都在）、图片块数量与本地一致。



| 错误 | 纠正 |
|-----|-----|
| 按论文章节顺序逐节摘要，读完不知道结论 | 结论摘要置顶，「取舍」明确到能否作为立项依据 |
| 论文说「实现 xxx」就照抄进记录 | 回到代码确认默认行为与开关，写出落差 |
| 引用数值只给结果不给算式和出处 | 附算式，区分正文/摘要页/README/示意图 |
| 把示意图文案当测量数据 | 以实验正文为报告工作点，图注写明差异 |
| 「未发现 xxx」写成「xxx 不存在」 | 限定在本次核查动作与核查日期 |
| 只讲机制不给例子，或例子是 A 记 A 的同义反复 | 一个多要素例子贯穿，并声明仅用于说明机制 |
| 定性案例当成效果证明 | 说明样本与盲测不足，流畅回答不能证明内部归因正确 |
| 借鉴建议没有验证条件 | 给出验证前提：固定回复模型、裁判、数据、上下文预算，逐项对比增量 |
| 只统计读取侧开销就宣称成本低 | 补上写入、归因、维护、无效预取的成本 |
| 大段翻译论文英文摘要 | 用自己的话中性转述，评价与转述分开标注 |
| 重要架构图只文字转述，读者无从核对 | 从 arXiv HTML 提取原图到本地嵌入，图随机制小节走 |
| 批量下载论文全部图片塞进记录 | 只嵌改变理解的 3-6 张，纯展示图不嵌 |
| 下载后不读图就嵌入，图-题错位或低清 | 每张用 Read 读图核对编号与清晰度，不过关则换提取路径或改文字转述 |
| 一览图用 AI 生图或自写 CSS，中文糊、字不可改 | 调用 hand-drawn-poster，文字交浏览器排版，截图后读图验收 |
| 一览图里出现正文没有的数字或更强结论 | 海报只做正文的视觉摘要，每个数字可回溯正文同值表述 |
